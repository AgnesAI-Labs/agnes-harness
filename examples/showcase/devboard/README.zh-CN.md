[English](README.md) | 简体中文

## 角色视角

切换「演示角色」，页面内容随之变化，不止按钮能不能点。角色视角只是视图：不改变谁能操作什么，服务端的校验也不变。

- **总览**顶部是「{角色}的工作台」：「待我处理」（审批节点、评审门、人工介入）、与该角色最相关的两三类未关闭记录（例如质量工程师看未关缺陷、8D、待审试验报告），以及最多五条「与我相关的紧急事项」（已超时的在前，其次按到期时间），点击跳到对应详情；项目卡片在下方，标题为「项目组合」。
- **需求与追溯、任务、变更、缺陷与测试、试验与首件、运维与质量**六页在列表上方有开关「只看与我相关（N）｜全部（M）」，默认只看与我相关，切换角色时恢复默认；本页没有与该角色直接相关的记录时，显示提示和「看全部」按钮，不显示空表。追溯页的「研发需求条目」视图不筛选。
- **项目**页不筛选，高亮与该角色相关的阶段（编写角色）和评审门（审批角色或阶段编写角色）。**研发全景**的「卡点责任角色」筛选默认为当前演示角色，该角色没有卡点时不筛选。**我的待办**不变。

规则写在 `client/lens.js`：质量工程师看到全部缺陷，机械设计师只看机械专业的需求，配置管理员看到配置基线，客服工程师只看来源为客服的预警；技术负责人、分技术中心主任、IPMT 还会看到所有等待他们决议的记录。没有规则的记录类型或角色一律视为「不相关」。

## 演示指引

每个页面顶部、「演示角色」旁边有「演示指引」按钮，点开后页面右侧出现指引面板。它不是弹窗，页面仍然可以操作，演示时观众能同时看到页面和说明。

- **全流程主线**：12 步讲清一个需求怎样变成可运行的项目。项目经理发起项目，IPMT 批准 CDCP，系统设计师做需求与追溯，技术负责人批准 TR1，软件设计师做设计与开发，技术负责人批准 TR3，TR4 在代码评审意见全部关闭后自动通过，验证工程师登记验收证据，质量工程师批准 TR5，IPMT 批准 ADCP。每一步标出由哪个角色操作，并带「切换为该角色」按钮。
- **我的角色**：当前演示角色的 4 至 6 步上手步骤，用到这个角色在种子数据里真实有的记录。切换角色，步骤随之变化；和主线有关的角色，最后一步指向它在主线中负责的步骤。
- 每一步写明「怎么做」「你会看到」「在实际工作中」。「带我去」跳到对应页面，并给目标位置加描边和一句说明，几秒后淡出，按 Esc 或点任意处立即消失。目标不存在时（例如本页没有与当前角色相关的记录），说明显示在页面标题旁。
- 主线第 2 步打开研发协调员，并在输入框里填好「新建并启动一个研发项目」，不会自动发送。真实模型跑完全流程要几十分钟，赶时间可以在总览页用「快进演示到…」，或者只演到 CDCP 或 TR1，后面用预置项目 PRJ-2025-019 讲。
- 主线第 7 步指向现场项目的「任务」页，第 12 步指向项目页的「交付成果」卡。
- 主线里程碑根据看板状态自动打勾：现场项目已建，CDCP、TR1、TR3、TR4、TR5、ADCP 的提交与批准。其余步骤点「完成，下一步」。
- 某个演示角色第一次进入时，面板自动打开「我的角色」，指向第 1 步。打勾、看过指引的角色和「不再自动打开」开关只保存在浏览器本地，不写入看板；「从头开始」清除主线和当前角色的打勾。
- 指引里的企业只有虚构的宁川装备；「在实际工作中」只写门系统制造企业的通用价值，由演示者对应到具体客户。

## 规则

所有写入都走 `domain.mjs` 的同一组函数，页面和智能体工具共用。

技术文件发布会按编制人的规范岗位排除校对角色，包括「软件设计师（架构）」或岗位后接姓名的写法；显式填写未知编制岗位时，须先更正才能发起流程。变更的 `note` 依据即使没有状态流转也保留在留痕中。

- **评审点档案**（`profiles.mjs`）按项目类型查表：订单项目（新造、改造、维保）走合同评审、设计联络（一）（二）、设计冻结、样机评审、型式试验评审、首件鉴定、交付验收；软件项目走 IPD 的 CDCP、TR1–TR6、PDCP、ADCP。一个阶段可以有多道门，按顺序进行：批准的不是最后一道时，阶段回到进行中并记「TR2 已通过，进入 TR3」；批准最后一道时阶段通过并生成基线。
- **裁剪**：`project.tailoring.skipped` 跳过相应的门。看板上新建的软件项目默认裁剪 TR2、TR6、PDCP；预置的 IPD 项目不裁剪。门编号为 `GATE-<项目>-<代码>-<序号>`。
- **审批人**：决议人的角色必须在门的审批角色里，否则提示「评审门不满足：本门需由 X 审批」；阶段的编写角色永远不能审批。会签门每个角色各签一次，全部签齐且意见全部关闭才批准，任一角色驳回即驳回（需填写意见）。TR4 标了 `auto`，代码评审意见全部关闭后自动通过。「系统检查」意见由审批人在决议时关闭（或随缺陷关闭、发布审批批准而关闭，自动门因此全部关闭时自动通过），提交方不能关闭。
- **试验**：PLANNED → IN_PROGRESS → REPORTED → APPROVED（REPORTED → IN_PROGRESS 为补试）。REPORTED 需有报告号和结论；不合格的试验只有关联变更已批准才能批准。提交型式试验或首件门时，每个尚未批准的同类试验自动加一条评审意见。
- **现场闭环**：预警 NEW → DISPATCHED → HANDLED → CLOSED；质量问题 OPEN → ANALYZING → ACTION → VERIFYING → CLOSED（进入 ACTION 需有根因且 D4 已完成；关闭需 D8 完成，并且关联变更已关闭或写明理由）。来源为现场或型式试验的变更，分析前必须有根因；批准后生成 ECN 和新的设计态基线，在役项目不返工；关闭前必须有验证；整改进度只增不减，完成后生成新的维护态基线。
- **审批流程**（`approvals.mjs`、`approval-templates.mjs`）：五类流程模板（技术文件发布、ECR、ECN 发布、质量问题关闭、试验报告），节点有串行、全部会签、或签三种模式。只有当前节点且角色在节点内的人能处理，否则提示「审批不满足：当前节点需由 X 处理」；同意、驳回（需意见，对象回到可编辑状态）、退回（上一节点、指定前序节点或发起人，之前的同意作废但留痕）、转办（同角色另一人）、加签（在当前节点后插入串行节点）、评论、撤回（仅发起人，且第一个节点还没人处理）。节点超过时限即「超时」，由当前时间派生，不落盘，总览与待办标红。一个对象同一时间只有一个进行中的流程。
  - 对象状态只能由流程推进：变更 CCB_REVIEW → APPROVED 只能由 ECR 批准触发（直接流转提示「需走 ECR 审批」），ECR 驳回则变更驳回；ECN 发布批准后才生成设计态基线；质量问题 CLOSED 只能由关闭流程批准；试验 REPORTED → APPROVED 只能由试验报告流程批准；已批准的试验、已关闭的质量问题，以及流程进行中的这两类对象都拒绝修改；技术文件发布批准后交付物才基线，发布流程进行中不接受新内容，提交评审门时本阶段还有未批准发布流程的交付物，门自动加一条评审意见，且该交付物不随阶段通过而基线。评审门的会签规则不变。
  - 智能体只能用 `devboard_approval_submit` 发起自己起草（含以某个角色身份起草）的对象的流程，以及由它提交 CCB 的变更（例如演示者交给它的客户变更）的 ECR，不提供处理动作；处理由人在「我的待办」完成。
- **追溯**：SWR 层允许 `SWR-`、`MER-`、`EER-`（软件、机械、电气）并带专业；CUS→SYS、SYS→SWR、SWR→TC 三段覆盖率；需求门提交时 CUS→SWR 不到 100% 会自动加一条评审意见。
- **变更**：SUBMITTED → ANALYZED（需有影响分析）→ CCB_REVIEW → APPROVED / REJECTED → IMPLEMENTED → CLOSED。**缺陷**：NEW → CONFIRMED → FIXING → RETEST → CLOSED，可延期处理。
- 第一版的需求、任务、人工介入状态机不变。store 的 schema 为 4；schema 3 的数据照常读取（审批集合为空），其他 schema 的数据读作种子数据，首次写入时替换（读取从不写入）。

## 智能体与现场项目

`coordinator`（研发协调员）带全部 21 个 `devboard_*` 工具、读写与 shell、`tool_search` / `tool_describe`、`subagent_spawn` / `subagent_list` / `subagent_collect`，以及技能 `devboard-playbook`（全流程、现场闭环、门代码与会签规则）。预设 `devboard` 允许在工作区内编辑与写入；所有 shell 命令（含 `node --test`、`node server.js`）都会请人确认，因为它们运行的是智能体自己写的代码；十一个声明式角色在新鲜子会话中共用父工作目录，权限取角色与父快照交集：系统设计师（需求）`requirements`、软件设计师（架构）`architect`、软件设计师（开发）`developer`、代码评审员 `reviewer`、验证工程师 `tester`，以及机械设计师 `mechanical`、电气设计师 `electrical`、诊断工程师 `diagnostics`、RAMS 工程师 `rams`、质量工程师 `quality`、配置管理员 `config`。代码评审员、质量工程师和配置管理员只读，其余角色可编辑文件；均没有 shell、看板或审批/签署能力，命令交回协调员执行。机械、电气、诊断与 RAMS 角色的分析文件放在 `devboard-projects/<项目编号>/analysis/<对象编号>/`，由协调员登记为 `ANALYSIS` 交付物；质量与配置角色只读，在答复返回编号意见，不创建文件。现场闭环按「诊断 → RAMS → 质量评审」派工；型式试验不合格时派机械或电气设计师写影响说明，再派配置管理员核对。十一个角色均列入 `delegableAgents`；采用应用前，须使用能在包检查时接受这份完整列表的平台构建。所有角色全过程中文叙述（用户明确选其他语言时遵从用户），业务状态用中文。

**快进。** 总览页「重置演示数据」旁边有「快进演示到…」，可选 CDCP、TR1、TR3、TR5（都停在待批）、「已完成」（ADCP 已批准）、**TR3 待批 + 客户变更**（TR3 待批，并已有一条客户变更在 CCB 评审、ECR 审批在「我的待办」等待）和 **TR5 待批 + A 类缺陷**（TR5 待批，有一条修复中的 A 类缺陷）。两个场景的取值是 `TR3_CHANGE` 和 `TR5_DEFECT`，输入仍然只有这个枚举。选择后打开研发协调员，输入框里已填好 `fast-forward` 快捷操作，由你点发送。协调员只调用一次 `devboard_fastforward`，它的输入只有这个门。工具每次都新建一个现场项目，把这一阶段该有的文件从包内样例 `assets/fastforward/`（关于虚构的「车门健康监测看板」的中文文档、无依赖且支持 `AGH_LOOPBACK_FD` 的 Node 应用、单元测试和浏览器验收记录）写到新目录 `devboard-projects/<项目编号>/` 下，并按真实顺序调用域函数推进看板、时间戳往前倒推几天，所以评审门规则、审批角色和追溯规则全部生效。目标门停在待批：到「我的待办」批准后点「继续推进」，就从这里接着往下做，文件已经在位。快进不会覆盖已有目录；项目编号以前用过时，改用下一个空闲编号。「重置演示数据」只清空看板，不删磁盘上的文件：要清理请自己删除 `devboard-projects/`。包因此新增了 `filesystem.write`（范围 `devboard-projects/**`，原来已有同范围的读权限），工具只写包内模板，不接受任何路径或内容。

**任务与缺陷。** TR1 批准后，playbook 要求协调员按 SWR 分组各建一个需求，每个需求建开发和测试两个任务，随角色工作置为进行中、已完成，并把每个失败的测试用例登记为缺陷，经修复中、待回归、已关闭流转。代码评审意见仍挂在 TR4 门上。快进出来的项目：TR3 起带任务，TR5 起带两条缺陷（一条已关闭，一条 B 级、等待回归）。

**面板 → 大模型 → 面板的实时闭环（3.7）。** 看板、输入框、大模型和看板在两个方向上接通。（1）工作按钮把对象交给协调员，协调员的第一个调用是 `devboard_handoff({type, id})`：人的决议、未关闭意见、下一阶段及其交付物、未完成的任务、缺陷和变更，长度有上限。平台的工作对象只带类型和编号（`openApplicationWork` 会丢掉其他字段），所以页面从 `devboard.handoff` 读同一份摘要，在你发送前显示在按钮旁边；任何内容都不会替你发送。（2）每个动作都有入口：从预警或质量问题起草 8D，从不合格试验起草变更（原来的直接起草改名为「手工起草」），分析已提交或已分析的变更，把已答复的人工介入交回，汇报项目进度。（3）每次工具写入在总览的**智能体动态**里留下一行，由服务端生成（最多 160 字符，保留最新 200 条），可选参数 `actingRole`（十一个 playbook 角色之一）显示在作者上；上次访问之后的新行会高亮。（4）`devboard_test_record` 接受 `results [{tc, status}]`：总数由系统计算，自报数字对不上就拒绝，通过的 TC 变为 VERIFIED，一个 SWR 的所有 TC 都通过后它也变为 VERIFIED，失败的用例列出来由协调员自己建缺陷。（5）`devboard_artifact_record` 还能登记 `CODE`、`TEST`、`ANALYSIS` 文件（在项目目录内，分析文件只能在 `analysis/<对象编号>/` 下），按纯文本预览，从不运行或渲染。（6）人决议评审门、走完审批流或答复人工介入后，总览和「我的待办」顶部出现「待交回研发协调员」卡片，一点就打开带好对象的输入框；协调员下次写该项目的看板记录后，或你点「忽略」，卡片消失。用真模型把整个流程（CDCP 到 ADCP）跑一遍仍是手工测试。

**客户变更与返工。** 现场项目从设计阶段起，项目页有「客户提出变更」按钮，先填变更标题、客户的理由和技术协议条款，看板登记这条变更（已提交，来源：客户），再打开研发协调员并填好 `customer-change` 快捷操作，由你点发送。协调员用 `devboard_handoff` 读这条变更（不会再登记另一条），用 `traceFrom` 沿追溯链推算影响（客户条款 → 系统需求 → 软件需求 → 设计条目和测试用例，以及它们涉及的交付物和代码模块；`devboard_change_upsert` 增加了这个可选参数，没有新工具），推进到 CCB 评审并发起 ECR 审批后停下。你在「我的待办」批准（先专业会签，再 CCB 决议）：受影响的需求变为 CHANGED，已通过**或正在评审**的受影响阶段回到返工，原来的门作废（还在待批的门被撤回）；点「继续推进」后协调员只改受影响的条目，重新提交各门并在说明里引用变更编号。变更详情页显示影响树。

**A 类缺陷卡住评审门。** 项目还有未关闭的 A 类缺陷（延期的也算未关闭）时，TR5 和 ADCP 不能批准。提交这两道门时，每条缺陷在门上加一条系统意见（B 类缺陷加一条可人工关闭的提示意见；TR4 不受影响）。批准时系统在最后一个签名前按缺陷本身再查一次，所以手动关掉系统意见也没用：拒绝提示会写明是哪条缺陷、修复并回归通过后才能批准。在「缺陷与测试」页把缺陷关闭后，门上引用它的意见自动关闭，关闭人记为「系统（缺陷已关闭）」。

**交付成果。** TR5 提交后或项目完成时，项目页出现「交付成果」卡：应用入口文件与启动方式、各级最近一次测试、测试报告和浏览器验收记录的预览，以及登记的运行地址（注明只在登记它的那次运行期间可访问）。「启动并打开」会打开研发协调员并填好 `run-app` 快捷操作：协调员按 playbook 经命令审批启动应用，登记它输出的地址，并保持运行到你说停止。「启动并打开」只是给协调员起草一条请求：要由演示者发送，并批准其中一条 shell 命令，地址才会出现，且只在这次运行期间有效。本地服务目前只在 macOS 沙箱下运行，请在演示用的 Mac 上提前排练；卡里的测试记录、测试报告和验收记录是静态文档，在任何环境都能看。页面本身不启动任何进程。

看板上新建的软件项目（默认类型）按 SOFTWARE 档案和默认裁剪推进，文件写在工作区的 `devboard-projects/<项目编号>/`，由研发协调员带领完成；订单类只建记录。角色子智能体只写文件，看板只由研发协调员登记。每过一道门，研发协调员提交评审后结束本轮；人在看板审批，再点「继续推进」，草稿里带上门编号，由人点发送。

现场闭环里协调员只起草：读取预警聚合（`devboard_fault_list`）和试验，起草 D2–D4 与变更影响分析并引用预警和试验编号，不关闭质量问题、不批准试验、不决议变更。

已授权的具名声明工具直接提供 schema，包括子智能体和后台任务工具，无需先 search/describe。保留 `tool_describe` 供获授权的 deferred schema 查询使用，不扩大协调员的工具白名单。

预设显式申请经审阅的 `sandbox.loopback_serve`：强制 L1、`on_unavailable: deny`、外网白名单为空，命令仍需审批。受支持的 macOS Host 先绑定 loopback socket，再传入 `AGH_LOOPBACK_FD` 与 `AGH_LOOPBACK_URL`；生成的 Node 服务必须用 `server.listen({ fd: Number(process.env.AGH_LOOPBACK_FD) })` 接管，并在就绪后输出该 URL。无 activation 的普通部署才使用 `127.0.0.1` / `--port` 分支。命令自行 bind 或主动连接仍被拒绝；不支持的沙箱后端拒绝该能力，不降级。现场演示须使用支持此能力的平台构建。

命令需要正确的工作目录：shell 默认 cwd 是工作区根目录，传真实存在的测试文件，如 `node --test devboard-projects/<项目编号>/test/unit.test.js`；或把 shell `cwd` 设为 `devboard-projects/<项目编号>/` 后用 `node --test` 自动发现。不要把 `test/` 目录作为位置参数。启动 `node server.js --port <空闲端口>` 同样设项目 cwd；AGH 中接管 Host listener 并读取实际 URL，普通部署才绑定 `127.0.0.1`。`--port` 不能指定 Host 分配的端口。禁止使用 4177/4178，无需外网或安装依赖。命令内 `curl` / `fetch` 不能主动连接此 listener，公开 HTTP 验收由真实浏览器执行，结果与 `node --test` 单元测试分别计数。

长文档分节写入：先用 `write` 创建标题、目录和章节占位，再逐节用 `edit` 追加或替换，每次约 2–4 KiB；每节写完用 `read` 核对。本小项目的 SAD 目标约 8–12 KiB，长章节继续拆分，不在一次模型输出中生成整篇。输出被截断就是交付未完成，不能算成功落盘。

每次 `subagent_collect` 前先调用 `subagent_list`，从本次返回逐字复制真实 child id；`subagent_spawn(wait=true)` 返回仍在运行时也如此。不得猜测或重建编号；收取后同时核对完成状态和实际文件。

8. `devboard-projects/<项目编号>/analysis/<对象编号>/` 工作目录与「分析文件不登记为交付物」的约定。
9. 研发全景的卡点（推断）：各类卡点的责任角色（未关闭意见与阶段超期归阶段编制角色，试验不合格未立变更归质量工程师，待 CCB 的变更归项目经理，维护态落后归配置管理员）、质量问题停在分析中的 7 天时限，以及角色到五个专业的归属（其余归「综合」）。
10. 审批流程的节点名称、角色与时限（均为推断）：技术文件发布 = 校对（24 h，设计类角色，不含编制人）→ 审核（技术负责人，48 h）→ 标准化审查（标准化工程师，48 h）→ 批准（分技术中心主任，24 h）；ECR = 专业会签（机械、电气、软件、工艺、质量全部同意，72 h）→ CCB 决议（技术负责人或分技术中心主任任一人，48 h），批准后生成 ECN；ECN 发布 = 配置核对（配置管理员，24 h）→ 批准（分技术中心主任，24 h）→ 发布（配置管理员，24 h）；质量问题关闭 = 质量审核（质量工程师，48 h）→ 批准（分技术中心主任，24 h）；试验报告 = 质量审核（质量工程师，48 h）→ 批准（技术负责人，24 h）。「标准化工程师」「工艺工程师」是新增的演示角色；加签节点时限按 24 h。

## 目录

- `profiles.mjs`：角色、组织、评审点档案与现场项目的默认裁剪。
- `approval-templates.mjs`、`approvals.mjs`：五类审批流程模板（纯数据）与流程规则（同意、驳回、退回、转办、加签、评论、撤回、派生超时）；与对象状态的衔接在 `domain.mjs`。
- `blockers.mjs`：从状态派生卡点（不落盘），供 snapshot 和研发全景页使用。
- `domain.mjs`：阶段、评审门、追溯、变更、缺陷、试验、预警、质量问题、基线、测试与第一版状态机；指标；存储（按 64 KiB 分块）。
- `seed-data.mjs`、`seed-docs/`：虚构项目组合的种子数据与文档正文。
- `handoff.mjs`：门、项目、变更、试验、预警、质量问题、人工介入的有长度上限的交接内容（`devboard_handoff`、`devboard.handoff`）。
- `fastforward.mjs`、`assets/fastforward/`：`devboard_fastforward` 工具，以及它写入的样例项目（文档、应用、测试、验收记录）。
- `index.mjs`：档案服务 `devboard.snapshot`、`devboard.artifact`、`devboard.transition`（含 trial、fault、problem、retrofit）、`devboard.create`、`devboard.gate`、`devboard.approval`（发起与处理审批）、`devboard.handoff`（只读交接摘要）、`devboard.handback`（收起交回卡片）、`devboard.reset`，智能体工具与技能。
- `skills/devboard-playbook.md`：研发协调员技能。
- `client/`：各页面，使用 `@agnes/web-ui` 组件（交付成果卡是 `result.js`，其纯函数在 `delivery.js`，快进选择器是 `fastforward.js`，「客户提出变更」表单是 `customer-change.js`，变更影响树是 `impact-tree.js`；智能体动态是 `activity.js`，交回卡片是 `handback.js`，交接按钮是 `work.js` 及其入口表 `entries.js`，分析文件列表是 `analysis.js`）。演示指引在 `guide.js`（面板、聚光）、`guide-memory.js`（浏览器本地记忆）、`guide-progress.js`（按看板快照自动打勾），文案是纯数据：`guide-data.js`（主线）、`guide-optional.js`（两段可选剧本）和 `guide-roles-*.js`（各角色）。
- `test/`：领域规则、插件契约与种子数据测试。

pnpm exec vitest run examples/showcase/devboard/test --maxWorkers=1
