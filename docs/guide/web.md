# Web workbench: manage tasks and extensions

English | [简体中文](web.zh-CN.md)

<a id="web-工作台集中管理任务与扩展"></a>

[Documentation](../README.md) · [First-time configuration](quickstart.md)

The Web workbench brings tasks, history, and administration into one local interface. Configure a model using the [quickstart](quickstart.md), then use this guide to understand task state, everyday management, and connections.

The [built-in browser](browser.md) plugin adds a switchable live Browser panel for web tasks and local-project testing. AGH and the panel operate the same backend page, with session isolation and explicit human takeover.

<a id="启动与连接"></a>

Transient errors appear in the top-right notification stack. Each expires after six seconds or can be dismissed with its labelled close button. Recovery, approval and account-repair actions remain visible until resolved. Stored artifact attachments retain their file labels in history; their internal URIs are not direct download links. Attachment hints use the shared tooltip on hover and keyboard focus; attachment failures distinguish size, pixels, file type and invalid data in the current language.

When an application page or workbench action requests a profile approval, the initiating browser opens a confirmation dialog over the current page. Review the plugin, operation, business object, revision and local expiry time before allowing once or rejecting. Closing the dialog or leaving the initiating page preserves the pending request. Confirmation does not dispatch the business operation automatically; continue through the original page using its existing operation receipt.

A compact **Needs attention** row with a count badge appears only for remaining profile decisions or automation runs, even without a selected conversation. It opens a separate dialog grouping scheduled tasks, triggers and plugin requests. Automation links open their run sessions; profile decisions can be allowed once or rejected in the dialog. Notifications from other clients never open a confirmation automatically. Missing operation titles use localized generic copy; technical identifiers remain in technical details. The inbox refreshes on change notices, focus, returning to a visible tab and reconnect, without periodic polling.

The main Web listener starts while its first Surface mount-table query runs in the background. Until that query succeeds, unknown Surface paths return HTTP 503 with a retry hint. A successful empty table means no mount; later query failures retain the last successful table. A persistent local connection receives lifecycle invalidations and reconnect events, then re-reads the authoritative table; healthy idle connections do not poll. Failed reads retry without overlap. Shutdown cancels the connection and drains the active read.

The topbar switches between Conversation and Trace with a sliding pill; the Trace activity dot appears while a turn is in flight. Its bug button opens Report a problem directly, and the rightmost icon toggles the workbench. Runtime info is in each sidebar session menu. That menu also offers Show in Finder (macOS), Show in Explorer (Windows), or Show in File Manager (Linux), named for the daemon’s platform. It opens only that session’s bound workspace on the daemon’s local desktop. Remote connections, headless desktops and missing workspaces return an error notice.

Project rows reveal **New session** and **…** on hover or keyboard focus. New session selects
that project's folder through the usual creation flow and skips the folder picker for an available
registered folder. The project menu can also show the folder in the native file manager, or
**Remove project…**. Removal asks for confirmation, archives the project's sessions under **Archived**,
and leaves all files on disk. Stop running sessions first. Adding the same folder again restores
the project listing; its sessions remain archived until restored individually.

The gallery promotes showcase applications. Missing flagship packages produce no placeholders or teaching-example fallback; new-session prompts use the same featured source. The [five developer teaching examples](../../examples/fde/README.md) remain in the plugin catalog and become accessible from Agents after deliberate installation.

## Start and connect

```sh
node agnes.mjs serve
```

Web listens on loopback and needs no login: open the plain URL that `serve` prints. The server checks Host and Origin against the address fixed at startup, so web pages on other sites cannot drive it; a `localhost` address on the same port is redirected to `127.0.0.1`. When changing the port, set a matching origin:

```sh
export AGNES_WEB_ORIGIN=http://127.0.0.1:4180
node agnes.mjs serve --port 4180
```

If an existing daemon has a different Origin, startup refuses to reuse it. Check its tasks, explicitly stop that instance, and restart. This entry point is a local workbench; this guide does not provide a public deployment or reverse-proxy login setup.

Session and approval traffic uses the browser SDK's direct WebSocket connection to the daemon. Resource/plugin management and plugin backend services use a same-origin HTTP BFF. Both belong to the local workbench; see the [communication architecture](../develop/architecture.md#the-two-web-communication-paths).

## Complete a task

1. Create a task from the sidebar and confirm the working directory in the creation dialog. Canceling the dialog does not create a session.
2. Select the current session's route/model in the model picker. Changing a provider default and changing a session's selection are separate operations.
3. Enter a message and click Send or press Cmd/Ctrl+Enter. Messages sent during a run are queued as follow-ups and run in order after the current turn completes. Stopping, a failed turn, or pending approval pauses automatic continuation and preserves unsent input. Sending a new message after a stop or failure resumes preserved input first, then the new message.
4. Queued messages appear above the input with their count and order, including after reopening or reconnecting. **Send now** stops the current turn and executes the selected queued message first; the other messages keep their order and continue after it completes. **Delete** removes only that pending message without stopping the current turn or starting queued work; the remaining messages keep their order. It removes the message from the execution queue, while its original event remains in session history. A message that has already started cannot be deleted or sent twice. If an action fails, its error appears beside the queue and the list refreshes.

5. Inspect tool arguments, results, and errors in their records. Reasoning text, tool state, and usage come from backend projections; the interface does not invent missing information. Retry appears only on the latest failed turn, and is unavailable for ledger-integrity failures or hook blocks.
6. When approval is requested, check the current choices and scope. Even when the request is outside the loaded history, its card loads the current decision and shows its details, offered actions, and relative expiry. If loading fails, use Locate approval to retry and load earlier history; once found, the approval card scrolls into view and receives keyboard focus. The card names who asked (package, role, MCP server) under its title, and under the choices lists what **Allow for this session** keeps (the first three scopes, the rest on hover), both as plain text. On a stored approval, **Reject with a reason** opens a one-line field (up to 500 characters; Enter rejects, Esc goes back) and the model reads the reason; an empty reason is a plain rejection, and a live prompt has no such field. After submitting, wait for backend confirmation; a disappearing button alone does not prove execution.

   One-call approval for AGH configuration and instruction files applies to tools that declare their write paths. Shell commands declare no targets: under full access, `echo ... > AGENTS.md` is not gated by that rule. Strong isolation is the sandbox’s job ([security](security.md#approvals)).
7. After clicking Stop, wait for backend confirmation. An already ended or parked turn can acknowledge Stop without another turn-end event. If confirmation takes more than 10 seconds or the request fails, the composer becomes editable and offers **Retry stop / Force end**. Force end resends cancellation through the independent control channel and reads the backend's stop record; lack of confirmation remains visible, and disconnecting is not treated as stopping. An active turn cancels pending approvals and aborts tools. Tool side effects that may already have happened remain unknown and are not replayed automatically.

The sidebar groups sessions by workspace, ordered by the most recent visible message (creation time for an empty session). It initially opens the newest nonempty group and loads five sessions. Show more adds five; Collapse returns to the first five. Closing a group releases its loaded list; expansion state lasts for the current page. The selected conversation remains open even when its row is outside the loaded page. A dot marks a running turn.

Once a group has loaded, background updates keep its rows and pagination control visible without a loading message. Pagination is disabled throughout the summary and page refresh, then uses the fresh cursor. Overlapping window-focus and page-visibility refreshes share one read. Unchanged first pages are reused; returning to the window, reconnecting, or manually retrying also checks for metadata changes such as renamed sessions. First loads and failures still show their status; a reload prompt appears only after refresh stops with stale data.

If a group changes after several pages have loaded, the list offers Reload instead of joining pages from different snapshots. Historical message summaries initialize in the background; initialization failures offer Retry. A failed or unfinished startup read does not count as empty history or automatically open a new-session dialog or first-run setup. Retry restores the list for selection and preserves any choice made while it was loading. Archived and inaccessible sessions are excluded before paging. Search remains independent of the loaded sidebar. The compose button on a folder row starts a session in that workspace, and the folder button beside the Workspaces heading adds a workspace. Press Shift+Cmd+O (Shift+Ctrl+O on Windows and Linux) to start a new session. The top bar shows the session title, its Agent and a runtime information button, followed by the Conversation/Trace switch and the workbench toggles.

In a new conversation, the workspace chip below the composer opens a searchable list of workspaces; **New workspace…** opens the full dialog to add one. Choose **×** on the chip (Work without a workspace) to start a chat instead. Chats run in one folder that Agnes keeps under its data directory, so every chat can see files written by another chat. Permissions, sandbox and hook trust are the same as in any workspace. Chats are grouped under **Chats** in the sidebar; that group cannot be removed or shown in the file manager. A new conversation started from an open chat is a chat too.

The sidebar lists **New conversation**, **Plugins**, **Agents**, **Automation**, then workspaces and conversation history. In the official UI, the footer shows only **Settings**; applications remain available from **Agents** and **Settings → Application**. When an app is adopted, the host-owned **Return to official UI** and **Switch application** entries remain available. Agents come from explicit plugin launch declarations; the built-in **General assistant** lets you choose a **Running mode** directly. Plugins use one inventory with **Source** and **Capability** filters, with separate **Skills** and **Connections (MCP)** tabs. Plugin rows explain their purpose and current status; registration details are collapsed under technical details. Settings groups are **General / Models / Permissions / Application / Advanced**; **Models → Run configuration** retains the execution configuration, including **Additional combinations for all conversations**. Application settings let you preview, adopt or clear an application. The Agents page follows the effective application’s visible-agent list and places its default agent first; execution bindings of existing sessions stay unchanged.

**Settings → Application** keeps application and interface previews on the same settings page; review their identity, visible changes, agents and permissions before adopting. The standard sidebar footer opens **Settings**; application recovery is available there and through Agents. **Settings → General** has separate palette, skin, font-size and language controls. Skin and language use keyboard-accessible pickers; palette offers System, Light and Dark. A saved skin choice survives a temporarily missing plugin and returns when that skin is available again; the host appearance is used in the meantime.

In **Settings → Application → Advanced interface choices**, preview and choose individual navigation,
conversation, composer, goal, interaction or deliverables implementations from trusted enabled plugins.
Rows show **Default / Application / Your choice**. **Restore default** removes just one role override.
Unavailable choices remain unresolved and fall back to the application or host. `/?admin` and
`agh app clear` clear the application and all role choices without changing execution settings.

On desktop, collapsing the sidebar keeps an icon rail for New conversation, Plugins, Agents, Automation and Settings. The icons keep the same actions, show their labels on hover or keyboard focus, and mark the current page. On narrow screens, closing the sidebar hides the drawer instead.

The thin ticks along the left edge of the conversation are the prompt navigator: one per prompt you sent, with the one you are reading drawn darker. All ticks stay short until the pointer enters the navigator, then nearby ticks lengthen; hover one to preview that prompt and the start of its answer, and click to jump to it with a brief highlight. Press Option+↑ / Option+↓ (Alt+↑ / Alt+↓ on Windows and Linux) for the previous or next prompt; when the window is narrow or the workbench leaves no room on the left, the ticks hide and the shortcuts still work. The bookmark button on the preview marks a prompt; bookmarks are saved with the session and show as a small dot beside the tick.

On the new-session home, an empty composer types sample tasks from the agent catalog. When **Tab Adopt** appears, Tab fills the draft and puts the caret at the end; it does not send the task. Typing, pasting or attaching pauses the examples until the composer is empty and unfocused again. Otherwise Tab follows normal focus navigation. Reduced motion keeps the normal static placeholder without Tab adoption. Find the examples themselves on the sidebar's **Agents** page.

The first message proceeds once the new session is ready; refreshing the sidebar does not block sending. A sidebar refresh failure is reported separately and does not restore an already submitted message as a draft.
Resource updates discovered during startup are prepared while the worker is idle. Updates discovered during a running turn remain deferred until before the next turn. Repeated Skill scans with unchanged resources do not trigger another worker reload.

A failed turn shows a localized explanation and any safe HTTP status/request ID. Transient failures offer **Retry**; rejected credentials or missing models offer account/model settings instead. Retry submits that turn's original user content through the normal send path, without replacing the current draft. It is unavailable while offline, opening, stopping or already running. Context, workspace, budget and step-limit failures require the indicated correction. Expand **Technical details** to copy the recorded code, reason, message and turn/session identifiers.

### Attach files and images

Click the paperclip beside Send, paste files, or drag them onto the composer. Up to 50 attachments are accepted, including empty files. Files and images upload originals in sequential 1 MiB chunks with progress, verification and Cancel. Originals are limited to 100 MiB per file and message; PNG/JPEG visual originals are additionally limited to 20 MiB and 64 million pixels. An interrupted upload can resume in the same live worker by selecting Retry; a worker restart requires a new upload. Intake expires after 30 minutes and is cleared on session close. Reloading the page requires selecting the source again. Generic files retain their declared MIME; visual images are validated against their bytes.

Original bytes belong to the selected artifacts provider. The server verifies the complete SHA-256 and returns a scope-bound pending receipt; prompt admission consumes it and stores a reference. The independent workspace upload API retains its own configured limits and `agnes-upload://` paths. Composer uploads do not require workspace write access. Dropping a completed draft removes its reference; its pending receipt remains a conservative GC root until expiry. Historical image cards lazily load authorized thumbnails, offer enlarged originals and original downloads, and display unavailable placeholders for missing or reclaimed data. Internal artifact URIs are never fetched directly.

A text-only model can receive image files without visual input. For a vision model, the artifacts provider caches model-specific renditions bounded by the 1456-pixel long edge and the model's stricter size limits. Originals, including valid JPEG trailers, remain byte-identical. The ledger and prompt transport carry references, not the original Base64. The `read` tool accepts `session-file://12/1` and `session-image://12/1`; `session-file://list` lists file references. Lookups enforce the current session, lane and inherited fork boundary. File names and read contents are untrusted data. Saving an original into the workspace still requires the normal workspace write authority.

The default-enabled `@agnes/document-reader` plugin adds `document_read` for PDF, DOC, DOCX and ZIP. PDF reads a selected page; pages without text use bundled offline Chinese/English OCR. For an incomplete text layer, `ocr: "always"` forces OCR; mixed PDFs are handled page by page. Word extraction returns text, including tables and notes, without reconstructing layout or embedded pictures. ZIP lists entry names first, then reads a selected text file or supported document without extracting onto disk. There is no ZIP-specific entry-count or aggregate expanded-size cap; a large unused member does not block other files. Selected documents share the reader's 100 MiB input budget, and text results are paginated; OCR pixels, execution time and worker concurrency are bounded. Macros, links and document instructions are not executed. Disabling the plugin removes this parsing capability while preserving uploaded files. OCR may misread text; encrypted, damaged or unsupported documents return an explicit error.

For PDF photographs, charts, and layout, `mode: "image"` returns one page image without OCR, along with any embedded text. Default `mode: "auto"` also returns a page image when text/OCR is empty; `mode: "text"` returns text only. Empty OCR does not prove a blank page. Page images use the existing authorized image channel and the selected model's image limits, including history. They are capped at a 1456-pixel long edge and 4 MiB; only the selected page is rendered. A text-only model can read extracted text but needs an available vision route to interpret page images. No new vision service is enabled automatically.

The installed pi-ai chat interface has text and image input only; it does not accept native file/audio/video blocks. Binary Excel and presentation files, audio, video and other unsupported formats can still be uploaded and saved, but a successful upload does not mean the model has read them. The agent must explain reading failures honestly. GIF and other image formats retain their original file bytes rather than being reduced silently to a single frame.

The model catalogue carries pi-ai `inputLimits` without a separate provider limit table; manual models may declare the same fields. Image counts follow the selected model’s declared limits; there is no universal four-image cap. Agnes models that support images accept at most four images in the complete request, including history and tool results. Model image byte limits count Base64 bytes separately from the 100 MiB decoded-byte cap. Images still exceeding limits after processing are rejected without clearing existing attachments; the complete batch is checked again before submission. Pending inputs share one queue record bounded by the 144 MiB transport frame, with 4 KiB reserved for its envelope. A queue already known to exceed the frame budget is refused before decoding its new media; admissible inputs still pass format validation and an exact UTF-8 frame-size check before storage. If the combined queue exceeds that budget, the new input is refused before storage; wait for a pending message to finish or remove one before retrying.

Attachments can be sent by themselves or with text. While a turn is running, the combination is queued as a follow-up. Images added to a text-only model are saved as file attachments and do not provide visual input. Changing models preserves the draft; native images prepared for an image model still need a compatible model to send. A failed send restores the text and attachments for retry; changing sessions clears staged attachments.

Long sessions preserve original images in their records. Selection uses model count, size and pixel limits, reserving the current turn first. Historical omission removes an oldest prefix in stable steps and records a watermark with the request, so wider model limits or a restart cannot revive previously omitted images. Missing historical originals degrade to a text placeholder; current-turn missing or corrupt bytes fail closed. Explicit image reads remain available through authorized tools.

To compare older pictures, ask the agent to inspect those originals. The existing `read` tool can list saved images with `session-image://list`, then reload a reference such as `session-image://12/1` or a batch such as `session-image://12/1,34/2`. The originals remain readable after context summarization. Reload batches must fit both the model and runtime media limits; compare large sets in smaller batches or select a model supporting the required simultaneous image count.

Before dispatch, the executing model is checked against the selected current, historical and tool-result images. Changing models preserves draft images; switch back or remove incompatible images before sending. Request bytes are checked in pi-ai’s provider payload callback and, for fetch transports, against the final HTTP body. Subsequent SDK wrapping can still trigger provider limits.

The local artifacts provider promotes inline image/file inputs to durable references before admission. ACP replays every stored image/file reference through standard resource links and bounded attachment metadata; inline compatibility uses standard embedded resources whose URIs are labels. Streamed Web originals also use artifact-backed references. The separate workspace upload API retains `agnes-upload://` identities. Reopening rebuilds previews and file cards through authorized reads. Optional providers retaining inline content remain subject to frame and projection budgets. `artifact.read` is a read-only API. Diagnostics and redacted exports omit original bytes; native raw exports keep verified originals in their companion artifact directory.

Open the model picker beside the composer. Models are grouped by account, with each model's capacity on the right. The “This session” rows show the current reasoning level, context window and auxiliary models. Open a row to edit it inside the same popover; Enter or Right opens it, Escape or Left returns, and Escape from the main panel closes it. Reasoning choices come from the current model. For context, choose automatic sizing, a capacity-valid preset or Custom. The custom field has a fixed K unit: `100` means 100,000 tokens. Clear it to restore automatic sizing. A choice applies immediately and closes the menu; a typed budget is committed on Enter or when leaving the field. Validation enforces the model's capacity. Settings apply to later requests and survive reopening.

Auxiliary model selects apply immediately to the current session, with a confirmation toast. “Follow defaults” names the actual default model; the Settings link opens Models & accounts → Auxiliary models. Defaults apply to new sessions; existing sessions keep their saved choices.

With no saved language choice, the interface follows the browser’s preferred language when supported (English or Simplified Chinese), otherwise English. A saved choice in Settings → General → Language takes precedence. Switching language also retranslates existing platform error and recovery notices; recorded tool output keeps its original text. Automatic titles use the language the model identifies in your first message: sending “Hi” produces an English title even in the Chinese interface. If the language is unclear, including mixed languages without a clear primary language or input consisting only of code, identifiers, numbers, or emoji, the model uses the interface language captured when that message was submitted. These language rules are prompt instructions; output is checked for format, without replacing its language or making another model request. Switching the interface language does not translate existing titles or overwrite manual names.

Failed turns show the recorded error code and message below their status, even when the process is collapsed. These details remain available after reopening the session. Older records without error details are labeled explicitly.

### Inspect the trajectory

Switch from Chat to Trajectory to review a session by turn and step. Select a record for its status, duration, error, and available token usage. The timeline offers four order and duration modes: drag to filter, scroll to zoom, right-drag to pan, and press Escape to clear the range.

Fold turns or tool calls, search the records, or load earlier history as needed. Tool arguments and results in **Projected content** are previews; choose **Full input** or **Full output** to read the recorded detail on demand. **Timing** shows recorded time fields. Missing timing, usage, or history is labeled rather than estimated.

On narrow screens, select timeline events from the record list. The chart remains an overview. Selected details use the full content area; Close details or Escape returns to the selected record. Switch back to Conversation to use the composer. Settings categories scroll horizontally, and composer chips wrap instead of shrinking their actions.

## Everyday management

The sidebar's **View options** menu groups sessions by workspace or shows one flat list, and filters them to hide archived sessions, show all conversations, or show archived sessions only. Choose **Archived only** under **Filter sessions** to show archived sessions by themselves. These filters show idle and completed sessions alongside running ones; they do not indicate that a task is executing.

Settings manages model accounts, plugins, Skills/MCP, appearance, and Computer Use. Available actions depend on backend capabilities and permissions. Installed plugins still require trust and enablement; see [plugin management](packages.md). Reopen history from the sidebar, or choose **Archived only** under **View options** for archived tasks. Archiving does not delete session history.

Computer Use shows driver status, system permissions, diagnostics, and maintenance progress. Switching settings pages keeps progress monitoring active. When the pane is replaced or reloaded, it reads the latest operation without resubmitting it. Removing the pane stops local monitoring; use Cancel explicitly to request backend cancellation and wait for confirmation. A connection error or a long wait does not confirm completion or cancellation.

To add MCP, describe the integration in chat and supply a service address or connection details, then inspect it in settings. New services must be trusted and enabled in sequence; see [MCP integration](mcp.md). Use the SecretRef configuration flow for credentials.

The URL's `session` parameter selects the session. Once a session opens, one-time example launch parameters are removed so refresh restores the current conversation. After a refresh or brief disconnection, the SDK reloads the projection from the backend without automatically resending business requests. If reconnection fails, inspect `daemon status`. After a daemon restart, open the normal URL printed by the current `serve` process. A running `serve` re-attaches by itself to a restarted daemon of the same home, profile and Web origin: while it waits, admin requests report the backend as unavailable (HTTP 503) rather than failing as internal, and the page reloads once the daemon is back. It never starts a daemon and refuses one with a different identity or Web origin; restart `serve` in that case. Local mode does not need to restore a startup token from sessionStorage.

Closing the browser, disconnecting the page, or stopping `serve` affects the client/Web service. Session facts determine whether backend tasks have ended. Run `daemon stop` separately to fully stop a trial instance.

### Scheduled tasks

The **Automation** page lists scheduled tasks. Each task has a target:

- **New session** (the default): every run opens a fresh session in the chosen workspace, named after the task and the start time, then runs the task there. You can also pick an execution mode or business agent, a preset and a model; unset fields use the defaults of a new chat. A business agent fixes its permission profile and model; the form displays those values and locks those choices.
- **Existing session**: the task is sent into one session when due. It starts a turn if the session is idle, or joins the running turn.

A one-time task stays in the default list while its run is still running or waiting for human attention, even after it has no further scheduled occurrence. Once the run finishes or fails, find it with **Include archived**.

Frequency is once, every N minutes or hours, daily, weekly, or a Cron expression, in this computer's time zone unless you name another. The form shows the next run before you save. Each row shows where the task runs, its rule, the next run, an on/off switch and the last outcome; the menu offers Run now, Edit and Archive. Run history lists each run as Running, Waiting for approval, Ran, Delivered or Failed, with its duration, a plain reason for a failure, and a link to the session. A run follows the normal approval policy: when it needs approval it waits like any session, and its history row links to it. A repeating task missed while this computer was off is made up once, for the latest run. When AGH stops or crashes in the middle of a new-session run, that run is not started again after the restart, since it may already have opened its session and sent the prompt: it is marked Failed with the reason that AGH stopped during the run, and a repeating task moves on to its next run. A run that had not yet started its session, and a task sent to an existing session, run again as before. The session's runtime dialog lists the tasks that session receives or created.

In chat, asking for recurring work ("every morning, summarize …") creates a new-session task in the current workspace; a one-off reminder ("remind me in 30 minutes", "continue this tomorrow") goes to the current session. The reply says where the task runs. See [schedule tools](../reference/default-tools.md).

### Results, search and run history

Switch between Tasks and Results on the scheduled-task page. Results collects finished run summaries, unread state, and links to the full session and its attachments. Mark a result handled or unread; this only changes its reading state and never answers an approval. A prompt delivered into a busy session remains Delivered, rather than being described as completed. Missing summaries are stated explicitly. Summaries contain up to 4,000 characters of the final assistant reply's text during the run, excluding thinking; the full output remains in the session. Refusal replies and text stopped by the output limit are retained too; failed runs keep their failure status and reason.

Search tasks by name or instructions, and filter by workspace, enabled, paused, ended, archived, failed or needs-attention status. Failed means the latest run failed; needs-attention includes outstanding human decisions. Status filters can include ended or archived tasks. Include archived controls the default list. Target, search, status and workspace filters are applied before the result limit. Search uses the same Unicode lowercase rule in the client and saved search field, including accented names. An empty filtered list still refreshes when a scheduled run becomes due or finishes.

View run history loads saved records newest first in pages of 20, with Load earlier records. All saved history stays on this computer without automatic age or count pruning, including archived tasks. New records snapshot the task's instructions, schedule and selected running settings; unspecified settings follow that session's defaults. Older records explicitly identify unavailable snapshots or summaries instead of substituting current settings. Records removed by older versions cannot be recovered. Task/order, global unread and task-specific unread indexes support seek pagination without offsets. When opening an existing local schedule database, missing search and receipt task fields are added and filled in a transaction; saved history, summaries and reading state are preserved. An empty database starts with the current structure. A failed read preserves loaded records and can be retried; late responses after switching tasks cannot replace the current history. An expanded history on its latest page follows the task list refresh. Loading earlier records pauses automatic replacement of that page; Refresh records returns to the latest page. Marking a result handled keeps the loaded pages and leaves older unread records accessible. On the latest page, results that finish while that mark is being saved appear after the response arrives.

## Current interaction boundaries

The built-in right-side document preview supports text, code, Markdown, filtered HTML, and images or PDFs delivered by the session resource service. A resource read failure displays a generic unavailable message; a reclaimed screenshot displays the retention-policy message. Replacing or closing the preview releases its acquired resource URLs and ignores late replies. Closing a preview does not cancel backend work. The workbench CSP permits local Blob URLs for images and frames; remote sources remain blocked, and PDF frames keep their sandbox. Other pages retain their existing CSP. Some browsers block their native PDF viewer inside a sandboxed frame; inline PDF preview is unavailable in those browsers.

Tool results use constrained previews and detail views. They cannot render arbitrary HTML. Do not assume every artifact supports upload, download, or rename, or that every message supports editing and regeneration. The interface exposes actions supported by the current backend. See [verification](../maintainers/verification.md) for the scope of real browser testing.

## Terminal and background jobs

Open a session and select **Terminal** in the workbench. The guide card starts a terminal with your last-used shell (zsh on macOS, pwsh on Windows, bash otherwise). Its chevron lets you choose another shell. With tabs open, **+** starts the remembered shell; right-click, long-press, or press Shift+F10 on **+** to choose a shell or attach an Agent job.

The xterm.js screen follows the app theme, preserves ANSI/OSC colors and fits the PTY when the panel resizes. Focus it to type, paste (up to 64 KiB of UTF-8 per paste), use arrow keys or Ctrl+C. Refresh reconnects to the same PTY. Double-click a human terminal's tab name, or choose **Rename** from its menu, to rename it; Enter or blur saves and Escape cancels. Names are stored in this browser per session.

Right-click a tab or press Shift+F10 to interrupt, inspect its session/job/working directory, or kill a human terminal. Its **×** ends a running process and closes the tab; an Agent tab's **×** only stops following. Closing the workbench detaches the UI and leaves processes running. Opening the workbench starts no terminal until you ask for one. A human terminal that nobody has typed into, viewed or received output from for 2 hours is closed, and so is an Agent's persistent shell after 30 minutes with no command running; background commands are never closed this way. Commands the Agent runs read their input from `/dev/null`, so a command that prompts for input fails instead of waiting forever. Agent jobs are read-only. Exit codes appear at the end of the screen with a grey tab dot for zero or red for nonzero. Capped-output and input-full notices appear in a dismissible strip. Output uses bounded snapshots: text missed between polls or before the retained tail cannot be recovered.

The legacy `/?settings=terminal` link opens the terminal in an available session workbench. If no session is open, it closes settings and asks you to open a session to use the terminal.

The background jobs settings page selects sessions by title, workspace and relative date, defaults to the current session and updates automatically. It shows shell commands, persistent interpreters, PTYs and subagent status and output. A running human-owned job can be stopped from its row menu after confirmation. Agent-owned jobs are read only here; ask the agent to stop them in their session. Every operation remains constrained by that session’s sandbox preset.

The shared terminal and background-job views use the session's pinned service binding for `jobs.read` and `jobs.control`. A replacement provider can serve that contract after the official provider is disabled in the session composition, or contribute its own client UI. Multiple providers for the same contract are refused. The platform still enforces process policy, session ownership, service grants and durable control receipts. Background-job management is also available under **Settings → Advanced → Jobs**.

The `agnes/jobs-web` extension needs `services` in its capability ceiling. New templates include it; older configurations can add it explicitly. Without that grant, shell/job tools still work but Web control is unavailable. Jobs survive page refreshes and turns, but are not recovered after a Host restart. Local PTYs support macOS/Linux; missing shells or providers without interactive execution report an error.

A saved web-search service can be ready without being the default. The search settings page offers **Use as the default provider** on ready services and explains why testing is unavailable until a default is selected. The configuration drawer exposes both the enabled and default controls; failed saves leave the previous search state in place.

## Reply suggestions

The built-in **Reply suggestions** plugin is enabled by default. Toggle it in **Plugins → Built-in** using the normal plugin controls. After a successful live reply, it uses the configured **Auxiliary model (fast)** to suggest one short next question as grey text inside the empty composer. Press **Tab** to fill it and edit before sending; typing hides it, **Escape** dismisses it for that turn, and empty **Enter** never sends it. Suggestions disappear on a new turn, session switch or reload. They are never added to the transcript or model context. Without an auxiliary model, or if generation fails or exceeds five seconds, no suggestion appears. Auxiliary usage is accounted for normally. Brand-new sessions retain the catalog task hints.

## Side-review heads-up

**Side-review heads-up** is off by default and is a per-session setting: open the session menu, choose **Runtime** and turn on **Side-review heads-up**. While it is on, a side model reviews the Agent's work after a side-effecting tool result (a command, a write, an edit or a delete) and at the end of each turn, and hands the Agent one short advisory note with its next model request. A review sends the conversation so far (the same view `/btw` sends), the latest user request and a truncated summary of the turn's tool calls (tool name, the first 200 characters of its arguments, ok or failed) to the **verifier model**, or to the **fast model** when no verifier is set; with neither configured nothing is sent. Each review is billed as a `side-call` cost row. The note, limited to 300 characters with control characters removed, reaches the Agent once, labelled as advisory and not a user instruction, and is also shown as a **Heads-up** banner above the composer after the turn, which you can dismiss. At most one review runs at a time, reviews during a turn are at least 20 seconds apart, a note already given is not repeated and at most 6 are produced per session per hour. It never blocks a tool, changes a permission or approves anything. Turning it off stops the review at once and drops a note that was not yet delivered. The switch belongs to the running session and is off again when the session is reopened. The terminal UI has the same switch as `/heads-up on|off`.
